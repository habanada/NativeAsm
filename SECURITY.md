# Security Policy

NativeASM is a low-level Win64 x86-64 machine-code generation and runtime instrumentation toolkit for Delphi.

The project is currently in alpha. APIs, supported instruction subsets, and internal implementation details may change.

## Supported versions

Security fixes are applied to the current development version of NativeASM.

Older commits, forks, locally modified builds, and third-party binaries are not maintained by this project.

## Reporting a security issue

Please do not publish exploit details in a public issue before the problem has been reviewed.

For a potentially security-sensitive issue:

1. Use GitHub private vulnerability reporting or a GitHub Security Advisory if it is available for this repository.
2. Include the affected commit or version.
3. Include the target platform and Delphi compiler version.
4. Include a minimal reproduction if possible.
5. Describe the expected and actual behavior.
6. Include crash addresses, generated bytes, register state, or disassembly when relevant.
7. State whether the issue requires attacker-controlled input.

For normal bugs that do not expose a security boundary, use the regular GitHub issue tracker.

## What to include in a report

Useful information includes:

- NativeASM commit hash
- Delphi compiler version
- Windows version
- CPU model
- enabled CPU features
- Debug or Release build
- exact exception or error message
- relevant generated machine code
- disassembly of the failing code
- minimal source code that reproduces the problem
- whether the failure is deterministic
- whether untrusted input is involved

For antivirus reports, also include:

- antivirus product and version
- exact detection name
- SHA-256 of the flagged file
- NativeASM commit used to build it
- compiler and build configuration
- whether the executable was built locally
- whether the detection is signature-based, heuristic, or machine-learning based

## Antivirus and heuristic detections

NativeASM generates and executes machine code at runtime. It also contains runtime instrumentation and debugging features.

These behaviors can resemble techniques that heuristic or machine-learning based antivirus products monitor, including:

- writable memory that later becomes executable
- runtime-generated machine code
- JIT code allocation
- software breakpoints
- runtime code patching
- instruction decoding
- low-level control-flow manipulation

As a result, locally built demos, tests, benchmarks, or tools may occasionally receive heuristic or machine-learning based antivirus detections.

A heuristic detection by itself does not prove that a binary is malicious. It also does not prove that the detection is a false positive.

Users should verify the source, build binaries locally when practical, and compare hashes when investigating a detection.

## Binary distribution

The source code is the primary distribution form of NativeASM.

If prebuilt binaries are published in the future, users should verify that they came from an official project release.

Locally built binaries can differ because of:

- Delphi compiler version
- linker settings
- build configuration
- optimization settings
- source revision
- local modifications

## JIT and executable memory

NativeASM intentionally creates executable machine code at runtime.

Code that works with executable memory must be treated carefully. Security-sensitive areas include:

- memory allocation
- page protection changes
- code finalization
- instruction cache handling
- bounds checking
- relocation and fixup calculations
- label resolution
- indirect calls and jumps
- lifetime of generated code buffers

Bugs in these areas can cause access violations, execution of unintended bytes, or control-flow corruption.

## Runtime instrumentation

NativeASM includes runtime instrumentation functionality such as software breakpoints and code inspection.

These features should only be used on processes, memory, and code that the user is authorized to inspect or modify.

Instrumentation code should not assume that arbitrary addresses are valid, writable, executable, or stable.

## CPU feature requirements

SIMD and specialized instruction paths must only execute when the required CPU feature is available.

Examples include:

- SSE2
- SSSE3
- SSE4.2
- POPCNT
- PCLMULQDQ

Incorrect feature gating can result in illegal-instruction exceptions on unsupported CPUs.

## Memory alignment

Some SIMD instructions require aligned memory.

Code must not assume that arbitrary strings, dynamic arrays, user buffers, packed structures, or offset pointers are naturally aligned.

Unaligned-safe instructions should be used unless alignment is explicitly guaranteed.

## Generated machine code

Correct instruction bytes do not automatically imply safe executable code.

Generated functions must also satisfy:

- Microsoft x64 calling convention
- stack alignment requirements
- shadow-space requirements
- volatile and nonvolatile register rules
- valid memory access
- valid branch targets
- correct fixup ranges

## Cryptographic showcase code

Cryptographic and big-integer code in the Showcase demonstrates NativeASM code-generation capabilities.

It is not presented as an audited cryptographic library.

Passing test vectors does not imply:

- side-channel resistance
- constant-time behavior in every path
- hardened key handling
- secure memory erasure
- resistance to fault injection
- production security review

Do not treat Showcase cryptographic code as a drop-in replacement for a reviewed production cryptography library.

## Test integrity

Security-related fixes must not be validated by weakening tests to match current behavior.

When a test changes, the reason should be independently justified.

Where practical, expected results should come from an independent source such as:

- published test vectors
- a reference implementation
- an independent parser or formatter
- an external assembler or disassembler
- a mathematically independent calculation

## Third-party material

NativeASM contains material derived from or inspired by third-party projects.

Relevant licensing and provenance information is documented in:

- `THIRD_PARTY_NOTICES.md`
- `Tools/ASMJIT_LICENSE.md`
- `Tools/ASMJIT_SOURCE.md`
- `Tests/ASMJIT_TEST_SOURCE.md`

Security reports concerning third-party source material should clearly identify whether the issue is in NativeASM-specific code, generated data, adapted tests, or upstream material.

## Responsible disclosure

Please allow reasonable time to investigate and fix a security issue before publishing detailed exploit information.

A useful report is specific, reproducible, and distinguishes between:

- compiler errors
- project configuration errors
- encoder validation failures
- invalid generated machine code
- runtime memory errors
- CPU feature problems
- test-design problems
- antivirus heuristic detections

This distinction helps security issues reach the correct layer of the project quickly.
